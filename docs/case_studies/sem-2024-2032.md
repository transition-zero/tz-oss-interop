# SEM 2024-2032 Validation

## The model

The Single Electricity Market Committee is the regulator for the all-island Irish market.
The Committee publishes the PLEXOS model that it uses for two purposes: Directed Contract
modelling and Capacity Remuneration modelling. NERA Economic Consulting supplies a
validation report and a backcast report with the model. The model covers nine calendar
years, from 2024 to 2032.

The report makes this model useful for a test. For each year, the report gives the demand,
the interconnector flows, the installed capacity for each technology, and the market
price. Thus you can compare a translation against exact values.

## Get the input

Download the model from the
[SEM-25-010 page on the SEM Committee site](https://www.semcommittee.com/publications/sem-25-010-sem-plexos-model-validation-2024-2032-and-backcast-report).
That page has three zip files. The
[Public Version](https://www.semcommittee.com/files/semcommittee/2025-03/SEM%20PLEXOS%20Forecast%20Model%202024-2032%28%20Public%20Version%29.zip)
zip file contains the XML file. The
[CSV Files 1 of 2](https://www.semcommittee.com/files/semcommittee/2025-03/SEM%20PLEXOS%20Forecast%20Model%202024-2032%20%28CSV%20Files%201%20of%202%29.zip)
zip file and the
[CSV Files 2 of 2](https://www.semcommittee.com/files/semcommittee/2025-03/SEM%20PLEXOS%20Forecast%20Model%202024-2032%20%28CSV%20Files%202%20of%202%29.zip)
zip file contain the traces.

The XML file looks for the traces in a `CSV Files/` folder. This folder must be adjacent to

## Translate and solve

If you did not install interop, install it now. Refer to
[Install](../../README.md#install).

Start interop:

```bash
uv run interop
```

Select `translate`. Then give these answers to the prompts:

| Prompt | Answer |
| --- | --- |
| Source framework | `plexos` |
| Destination framework | `pypsa` |
| Pipeline | `plexos-to-pypsa` |
| the PLEXOS `<MasterDataSet>` input XML | `case_study_inputs/sem-2024-2032/PUBLIC Validation 2024-2032 Model 2025-03-14.xml` |
| which PLEXOS Model to translate | `Opt A 24-32 (Avail, Uplift, Wheeling)--MIP` |
| a four-digit year such as 2026 | `2026` |
| Output | `outputs/sem-2026.nc` |
| the extensions sidecar | `outputs/extensions.json` |

The model covers nine years, but the translator writes one year at a time. Thus the year
prompt selects the year. You can give any year from 2024 to 2032.

Then select `solve`. Give the model type `pypsa` and the network `outputs/sem-2026.nc`.
Select an output directory. Leave the start date and the end date empty, because the solve
must cover the full year. Give the unit commitment `linearised`. Keep the default window
and the default look-ahead. For more data about these prompts, refer to
[the solve tutorial](../tutorials/solve.md#pypsa-path).

### The Sienna path

The same model also translates to a Sienna system, which is what a partner running
PowerSimulations.jl needs. That translation is a run of its own, with its own mappings file.

Write `inputs/plexos_user_mappings.yaml` in PLEXOS words. It needs one row for each of the
21 Fuel objects and each of the 17 generator categories in this model. `interop init`
scaffolds a starter file at that path, and
[the mapping document](../translation_mappings/translation-from-plexos-to-sienna.md#the-carrier-mappings-file)
states the shape of a row.

Select `translate`. Then give these answers:

| Prompt | Answer |
| --- | --- |
| Source framework | `plexos` |
| Destination framework | `sienna` |
| Pipeline | `plexos-to-sienna` |
| User mappings file | `inputs/plexos_user_mappings.yaml` |
| the PLEXOS `<MasterDataSet>` input XML | `case_study_inputs/sem-2024-2032/PUBLIC Validation 2024-2032 Model 2025-03-14.xml` |
| which PLEXOS Model to translate | `Opt A 24-32 (Avail, Uplift, Wheeling)--MIP` |
| a four-digit year such as 2026 | `2026` |
| the SiennaSchemas system.json | `outputs/system.json` |

That run writes three files: `outputs/system.json`, its HDF5 companion
`outputs/system_time_series_storage.h5`, and `outputs/extensions.json`. Those three files
are the product. The system holds 3 `ACBus`, 3 `Area`, 3 `PowerLoad`, 66 `ThermalStandard`,
20 `RenewableDispatch`, 32 `EnergyReservoirStorage` and 4 `TwoTerminalGenericHVDCLine`
components, over 8,760 hourly snapshots.

To prove that the system dispatches, run `translate` a second time over those three files:

| Prompt | Answer |
| --- | --- |
| Source framework | `sienna` |
| Destination framework | `power-simulations` |
| Pipeline | `sienna-to-power-simulations` |
| the SiennaSchemas system.json | `outputs/system.json` |
| the HDF5 time-series sidecar | `outputs/system_time_series_storage.h5` |
| the extensions sidecar | `outputs/extensions.json` |
| the PowerSystems.jl system.json | `outputs/power_simulations_system.json` |
| the HDF5 time-series sidecar | `outputs/power_simulations_system_time_series.h5` |

Then select `solve`. Give the model type `sienna` and the system
`outputs/power_simulations_system.json`. Give the network model `dcp`, the unit commitment
`linearised`, and the HiGHS defaults. Leave the time limit empty. For more data about these
prompts, refer to [the solve tutorial](../tutorials/solve.md#sienna-path).

The Sienna solve takes no date range, so it covers every snapshot in the system, which is
the whole of 2026.

## The headline number

**What you can check by yourself.** The translation completes, and the solve gives the
status `optimal`. The translator writes a `decisions.md` file adjacent to the network.
That file gives each source field, the destination field for it, and each component that
the translator did not translate.

| Year | Path | Unit commitment | Status | Objective |
| --- | --- | --- | --- | --- |
| 2026 | PyPSA | linearised | optimal | EUR 4.16316 × 10⁹ |
| 2026 | Sienna | linearised | SUCCESSFULLY_FINALIZED | EUR 8.22297 × 10⁹ |
| 2026 | Sienna | exact | SUCCESSFULLY_FINALIZED | EUR 8.63559 × 10⁹ |

The `exact` Sienna solve stopped at a gap of 0.0815%, inside the 1% tolerance the solve
applies, so that objective is proved to within 0.1%.

The PyPSA objective and the Sienna objectives are not the same quantity, so do not read the
difference as an error in either path. The PyPSA solve rolls one month at a time with a
look-ahead, and its `linearised` answer keeps each start cost and each minimum up and down
time as a continuous fraction. The Sienna solve covers the year in one window, and its
`linearised` answer is economic dispatch, which applies neither. Refer to
[the gap analysis](../translation_mappings/plexos-to-sienna-gap-analysis.md#unit-commitment-relaxed).

**What we measured.** We compared the translation against the values in the NERA
validation report:

| Check | Result |
| --- | --- |
| Demand anchors and interconnector anchors | Equal to the published report |
| Wind capacity, all nine years | Within 1.8% |
| Solar capacity, all nine years | Within 4.3% |
| Market price, 2026 | 8.9% less than the report |
| Market price, 2032 | 10.9% less than the report |

We measured these values on 2026-08-18, on branch `caiso-compare-dataset-v2`, at interop
version 0.1.0. The software that makes this comparison is not in this repository. Thus you cannot
do this comparison again from this repository. But you can do the translation and the solve
again, as shown above.

**These prices pre-date three changes to the generator translation**: reading start fuel,
committing a generator that states a minimum output, and holding a written number to six
decimal places. Each moves the dispatch, so measure again before you compare a new run
against the row above.

## What the number does not cover

A solve keeps no reserve headroom. The translator puts the reserves in the sidecar file
that you named at the last translate prompt, but nothing applies them. Thus the dispatch
is less constrained than the dispatch in the source model. This is one possible cause of
the price that is less than the report.

Nothing applies a PLEXOS `Constraint` either. This model caps the energy of each river
system of its hydro fleet, and the running hours of several peakers, with `Constraint`
objects, and PyPSA has no home for any of them. Those resources are therefore free to run
at nameplate all year, which is a second possible cause of the price that is less than the
report. The translation reports every one of them, so read the not mapped entries of
`decisions.md`.

The network has no load shedding resource. Thus if the capacity is less than the load in
one hour, that window does not solve. The solve does not report a shortfall.

The Sienna path keeps no reserve headroom either, and it does worse: a `plexos-to-sienna`
run writes no reserves file at all, because the first leg writes that file inside the run's
scratch space. Run `plexos-to-pypsa` on its own if you want the reserves.
[The gap analysis](../translation_mappings/plexos-to-sienna-gap-analysis.md) lists every
other thing the Sienna path loses, and what each loss does to the dispatch.

## What it costs

The download is 39 MB (37 MiB), and it unpacks to approximately 117 MB. A laptop can
translate and solve one year.

The Sienna path costs about the same to translate. The solve takes more compute, because it
covers the whole year in one program. The network model `copperplate` is faster than `dcp`,
and `linearised` is faster than `exact`.

The first solve of a session also downloads Julia and the PowerSimulations.jl packages.
