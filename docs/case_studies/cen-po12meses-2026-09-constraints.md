# The custom constraints of the CEN model

This page classifies the 509 `Constraint` objects in `DBSEN_202609_PO12meses.xml`, the model
of [the CEN case study](cen-po12meses-2026-09.md). A class names what a constraint represents.
Constraints that do the same thing have the same class. For each class, the page gives the
SiennaSchemas 0.2 type that can hold it, if there is one.

## How to read the tables

### The words in the descriptions

| Word | PLEXOS property |
| --- | --- |
| units on | `Units Generating Coefficient` of a `Generator` |
| output | `Generation Coefficient` of a `Generator` |
| units out of service | `Units Out Coefficient` of a `Generator` |
| units that provide reserve | `Reserve Units Coefficient` |
| regulation-raise reserve, regulation-lower reserve, raise reserve, lower reserve | The reserve provision coefficients of a `Generator` or a `Battery` |
| provision | `Provision Coefficient` of a `Reserve`: the total provision of that reserve |
| charging, discharging, stored energy | `Load Coefficient`, `Generation Coefficient` and `Energy Coefficient` of a `Battery` |
| demand | `Load Coefficient` of a `Node` |
| end volume, release, release to generators, natural inflow | The coefficients of a `Storage` with the same names. In a gas `Storage`, "release to generators" is the gas that the generators draw. |
| value | `Value Coefficient` of a `Decision Variable` |

A **variant** is one of a set of objects whose names are the same except for the end: `_DIE`,
`_GN_A` to `_GN_F`, `_GNL_A` to `_GNL_G`, `_GNL_INF`, `_GNL_P` or `_GLP`. In a set of generators,
each variant is one configuration on one fuel. In a set of gas `Storage` objects, each variant is
one gas supply. The descriptions show a set of variants as one item, for example "`KELAR-TG1` (13
variants)".

A **timeslice** code limits a value to some periods. `M` is the month, `H` is the hour, `W` is the
day of the week and `D` is the day of the month. A comma means "and", and a semicolon means "or".
For example, `M1-3,H11-18` means the hours 11 to 18 in the months 1 to 3.

### The column "In `MT_base4s`"

The case study translates the model `MT_base4s`. This column tells you if that model includes the
constraint.

- **Yes.** The model includes the constraint.
- **No.** The property `Include in MT Schedule` of the constraint is 0 for the scenarios of
  `MT_base4s`.
- **Yes, but its RHS is only in scenario X.** The model includes the constraint, but each row of
  its right-hand side belongs to a scenario that `MT_base4s` does not hold. The description shows
  the value that the XML file writes.

### The column "What it does"

The description uses the data that `MT_base4s` reads. A row of a scenario that `MT_base4s` holds
replaces the row with no scenario. Where a value comes from a data file or a `Variable`, the
description names the source. I did not read the data files.

## What I assumed

1. **A constraint with no `Sense` is an equality.** The XML file gives the property `Sense` the
   default value 0, and 0 is "equal to".
2. **A `Reserve` with no coefficient selects the reserves.** Many constraints link a `Reserve`
   and give it no coefficient. I read that link as the set of reserves that the provision
   coefficients count. The descriptions show it as "(counted for reserve X)". I did not confirm
   this against the PLEXOS documentation.
3. **The Sienna destinations come from SiennaSchemas 0.2 only.** I read the types and their
   descriptions in `power-openapi-models` 0.2.0. I did not check that PowerSimulations.jl applies
   each field in a solve.

## The classes

Each class has two descriptions. "What the constraints do" states the constraint in model terms.
"In plain words" states it for a reader who does not know PLEXOS.

## Points to check

1. **`CRCA_BAT_EL_TRIGAL_FV` has the reverse signs.** The 103 other constraints of the class
   "Battery charges from its own plant" limit the charging to the output of the plant. This one
   limits the output of `EL_TRIGAL_FV` to the charging of `BAT_EL_TRIGAL_FV`.
2. **12 constraints always hold.** Each weight has the sign of the limit, so the sum always meets
   it: `COLBUNleaks`, `Cipreses_IfDeficitMaule_NoDeficitInv_2`, `Inv_CotaFija_lb`,
   `TEMP_MauleVarActivate`, `CSF_MinUnitsNorth`, the six `Special...North` constraints and
   `CPF_DownMinProvision`.
3. **`CPF_DownMinProvision` does not use the requirement that `CPF_DownCalculation` calculates.**
   It links `CPF5mDown_Requirement` with no coefficient, so the lower reserve has no calculated
   requirement.
4. **`RALCOmaxrelease_e1` and `RALCOmaxrelease_e2` set no limit.** The variables `RALCOmax_v1`
   and `RALCOmax_v2` have no upper bound and no cost. `MT_base4s` does not include these
   constraints.
5. **`CAMPICHE_Starting` and `PILMAIQUENeco` have no coefficient.** `CAMPICHE_Starting` states
   0 = 1 in the hours 16 to 20.
6. **`BIOENERGIASmaxGN` has only coefficients of 0.**
7. **17 constraints name a pre-calculation.** Their PLEXOS descriptions contain "PRECALCULO",
   and some say that the pre-calculation changes the right-hand side. So the values in the XML
   file can differ from the values of a run. These are the three `...leaks` constraints and 14
   constraints of the water rights of the Maule basin.
