## Decisions that changed a contract or a convention

### The `infrastore` bound reverses the choice the owner made earlier in the day

**The owner chose a floor alone, `infrastore>=0.14.1`, and this run sets
`>=0.14.1,<0.16`.** The owner should read this entry first, and can reverse it.

The finding: CodeRabbit, `pyproject.toml:37`, Major. It said that a clean install can
resolve a release that fails to open a Sienna sidecar written under 0.14.1.

The owner chose the floor on a premise that this run disproved. The premise was that this
repository documents no infrastore format contract, and that the code only reads time
series through the package's API. A round trip between two installed releases shows the
contract is real:

- `infrastore` 0.14.1 writes `initial_timestamp` as `2030-01-01T00:00:00Z`.
- `infrastore` 0.16.0 validates each association row against the **SiennaSchemas 0.4**
  wire contract, and 0.17.0 against **0.5**. Both reject that form.
- This repository's input contract is SiennaSchemas **0.2**, which
  `power-openapi-models<0.3` already states.

So `infrastore`'s version selects a SiennaSchemas wire contract. It is not an independent
dependency, and a floor alone lets a fresh install resolve a release that cannot read the
sidecar an older install wrote.

**The option taken:** `infrastore>=0.14.1,<0.16`. It is still wider than the `==0.14.1`
that the branch replaces, because 0.15.1 reads a 0.14.1 sidecar.

**The options rejected:**

- *A floor alone, `>=0.14.1`, as the owner chose.* This would be right if infrastore's
  version did not select a wire-contract version. The round trip below shows it does.
- *`<0.15`.* This would be right if 0.15.1 also rejected a 0.14.1 sidecar. It does not;
  it reads the values back.
- *Keep `==0.14.1`.* This would be right if 0.15.1 were untested. It is tested and it
  works, so the exact pin is narrower than the evidence supports.
- *A runtime version check instead of a bound.* This would be right if the repository had
  somewhere to put one that every entry point passes through, and if a late failure were
  acceptable. Metadata states the constraint before the install, which is earlier and
  cheaper.

**The blast radius:** one line of `pyproject.toml`, `uv.lock`, and the published metadata
of `tz-oss-interop`. No code changes. The locked version stays 0.14.1, so no test
behaviour changes.

**The evidence**, run in two clean virtual environments on Python 3.12:

```
# writer = infrastore 0.14.1, mirroring interop/plugins/sinks/emit_sienna_h5_sidecar.py
wrote 1 association rows, initial_timestamp "2030-01-01T00:00:00Z"

# reader, mirroring interop/plugins/sources/stage_sienna_system_json.py
infrastore 0.14.1  opened the store, imported the rows, read [1.0, 2.0, 3.0, 4.0]
infrastore 0.15.1  opened the store, imported the rows, read [1.0, 2.0, 3.0, 4.0]
infrastore 0.16.0  InvalidParameterError: ... does not match the SiennaSchemas v0.4.0
                   wire contract: /initial_timestamp
infrastore 0.17.0  InvalidParameterError: ... does not match the SiennaSchemas v0.5.0
                   wire contract: /initial_timestamp
```

`infrastore` 0.16.0 is self-consistent: it writes `2030-01-01T00:00:00` without the `Z`
and reads that back. The break is only across versions, which is exactly the case a
published library's metadata has to state.

The commit is in the round 1 entry below.

#### Finding 1, `pyproject.toml:37`, Major, verdict `act`

> **Bound the `infrastore` range to releases that read sidecars written under 0.14.1.**
> The range `>=0.14.1` also admits later `infrastore` releases. The upstream file-format
> reference states that a store one format version behind can be rejected on open, and
> that the 0.16.0 release adds a column. A clean install can therefore resolve a release
> that fails to open an existing Sienna sidecar written under `infrastore==0.14.1`. The
> repository has no version check that would catch this. Set an upper bound, or another
> constraint, that excludes releases that cannot read those sidecars. Issue `#182`
> requests this compatible upper bound. The exact bound depends on which upstream release
> is verified to read the existing format, so choose it after checking that release
> against a sidecar written under 0.14.1.

[`https://github.com/transition-zero/tz-oss-interop/pull/183#discussion_r4627279918`](https://github.com/transition-zero/tz-oss-interop/pull/183#discussion_r4627279918)

The conclusion is right and the stated mechanism is not. The sidecar **opens** under
0.16.0 and 0.17.0. What fails is `import_time_series_associations_openapi`, which
validates the rows against a newer SiennaSchemas wire contract. CodeRabbit asked for the
bound to be chosen by running the check, which this run did. See the contract decision
above for the evidence and the rejected alternatives.

#### Finding 2, `.github/workflows/publish.yml:185`, Minor, verdict `act`

> **Allow the publish job to resume after a partial upload.** If the library upload
> succeeds and the harness upload fails, a rerun uploads the library again first. The
> action defaults `skip-existing` to `false`, and PyPI rejects a file that already exists.
> The library step fails, so the job stops before the harness step. The same rejection can
> occur for a second file within one distribution. Set `skip-existing: true` on both
> upload steps. Keep the library-first order.

[`https://github.com/transition-zero/tz-oss-interop/pull/183#discussion_r4627279876`](https://github.com/transition-zero/tz-oss-interop/pull/183#discussion_r4627279876)

Correct, and the two-upload shape is what makes it bite: the harness upload is the one
that can fail after the library succeeded. CodeRabbit raised the one real objection
itself, that `skip-existing` matches by filename and not by content, and answered it: a
re-run downloads the same artefacts that the smoke proved, so a skipped name is the file
that was tested. The library-first order is kept.

The same thread carried a `zizmor` tool warning, that `publish.yml` has no top-level
`permissions` block, so two jobs take the repository default. Acted on in the same
commit: a top-level `permissions: contents: read`. A job that needs more already declares
its own block, which replaces the default rather than adding to it, so
`build-and-publish` and `publish-pypi` are unchanged.

#### Finding 3, `docs/developer_documentation/release.md:78`, Minor, verdict `act`

> **Give pip users the correct prerelease option.** The sentence applies
> `--prerelease=allow` to both installers. For pip, document `--pre` instead.

[`https://github.com/transition-zero/tz-oss-interop/pull/183#discussion_r4627279902`](https://github.com/transition-zero/tz-oss-interop/pull/183#discussion_r4627279902)

Correct. `--prerelease=allow` is uv's option and `--pre` is pip's. The sentence named one
for both.

#### Finding 4, `docs/developer_documentation/release.md:79`, Minor, verdict `act`

> **Do not promise that the rehearsal requires consumer opt-in.** If the new distribution
> has only a release candidate, an ordinary uv installation can select that release
> candidate without `--prerelease=allow`. The documented rehearsal can therefore become
> the version that ordinary consumers install. uv explicitly permits this fallback when no
> stable candidate is available. State this first-release limitation and remove the claim
> that the rehearsal is an unused version.

[`https://github.com/transition-zero/tz-oss-interop/pull/183#discussion_r4627279891`](https://github.com/transition-zero/tz-oss-interop/pull/183#discussion_r4627279891)

Correct, and it matters because the first rehearsal is the one the release page tells the
owner to run. Two resolutions prove both halves, so the fix scopes the claim rather than
deleting it:

```
# only an rc on the index, no flag
uv pip install --no-index --find-links dist interop-prerelease-probe
 + interop-prerelease-probe==0.1.0rc1

# a stable 0.1.0 and a newer 0.2.0rc1 on the index, no flag
uv pip install --no-index --find-links dist interop-prerelease-probe
 + interop-prerelease-probe==0.1.0
```

So the claim holds for every release after the first and fails for the first. The page now
states the rule, gives each installer its own option, and carries a warning that names the
window between the rehearsal tag and the release tag.
