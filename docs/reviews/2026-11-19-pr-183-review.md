### The `infrastore` bound reverses the choice the owner made earlier in the day

**The owner chose a floor alone, `infrastore>=0.14.1`, and this run sets
`>=0.14.1,<0.16`.** The owner should read this entry first, and can reverse it.

The finding: CodeRabbit, `pyproject.toml:37`, Major. It said that a clean install can
resolve a release that fails to open a Sienna sidecar written under 0.14.1.

The owner chose the floor on a premise that this run disproved. The premise was that this
repository documents no infrastore format contract, and that the code only reads time
series through the package's API. A round trip between two installed releases shows the
contract is real:

- `infrastore` 0.14.1 writes `initial_timestamp` as `2030-01-01T00:00:00Z`.
- `infrastore` 0.16.0 validates each association row against the **SiennaSchemas 0.4**
  wire contract, and 0.17.0 against **0.5**. Both reject that form.
- This repository's input contract is SiennaSchemas **0.2**, which
  `power-openapi-models<0.3` already states.

So `infrastore`'s version selects a SiennaSchemas wire contract. It is not an independent
dependency, and a floor alone lets a fresh install resolve a release that cannot read the
sidecar an older install wrote.

**The option taken:** `infrastore>=0.14.1,<0.16`. It is still wider than the `==0.14.1`
that the branch replaces, because 0.15.1 reads a 0.14.1 sidecar.

**The options rejected:**

- *A floor alone, `>=0.14.1`, as the owner chose.* This would be right if infrastore's
  version did not select a wire-contract version. The round trip below shows it does.
- *`<0.15`.* This would be right if 0.15.1 also rejected a 0.14.1 sidecar. It does not;
  it reads the values back.
- *Keep `==0.14.1`.* This would be right if 0.15.1 were untested. It is tested and it
  works, so the exact pin is narrower than the evidence supports.
- *A runtime version check instead of a bound.* This would be right if the repository had
  somewhere to put one that every entry point passes through, and if a late failure were
  acceptable. Metadata states the constraint before the install, which is earlier and
  cheaper.

**The blast radius:** one line of `pyproject.toml`, `uv.lock`, and the published metadata
of `tz-oss-interop`. No code changes. The locked version stays 0.14.1, so no test
behaviour changes.

**The evidence**, run in two clean virtual environments on Python 3.12:

```
# writer = infrastore 0.14.1, mirroring interop/plugins/sinks/emit_sienna_h5_sidecar.py
wrote 1 association rows, initial_timestamp "2030-01-01T00:00:00Z"

# reader, mirroring interop/plugins/sources/stage_sienna_system_json.py
infrastore 0.14.1  opened the store, imported the rows, read [1.0, 2.0, 3.0, 4.0]
infrastore 0.15.1  opened the store, imported the rows, read [1.0, 2.0, 3.0, 4.0]
infrastore 0.16.0  InvalidParameterError: ... does not match the SiennaSchemas v0.4.0
                   wire contract: /initial_timestamp
infrastore 0.17.0  InvalidParameterError: ... does not match the SiennaSchemas v0.5.0
                   wire contract: /initial_timestamp
```

`infrastore` 0.16.0 is self-consistent: it writes `2030-01-01T00:00:00` without the `Z`
and reads that back. The break is only across versions, which is exactly the case a
published library's metadata has to state.

##### Finding 5, `Dockerfile:26`, Minor, verdict `act`

> **Track the version override in the uv cache key.** `uv` uses default cache keys for the
> local project, and `SETUPTOOLS_SCM_PRETEND_VERSION` is not one of them. A retained
> builder with a persistent `/root/.cache/uv` mount can therefore reuse a wheel built with
> an earlier `VERSION` (for example `0.2.0rc1`) after the same checkout is rebuilt with a
> new `VERSION`. The image label then reports the new version while the installed metadata
> reports the old one.

[`https://github.com/transition-zero/tz-oss-interop/pull/183#discussion_r4627968188`](https://github.com/transition-zero/tz-oss-interop/pull/183#discussion_r4627968188)

Correct, and it survives the obvious objection. Docker's own layer cache **does**
invalidate, because `ENV SETUPTOOLS_SCM_PRETEND_VERSION=${VERSION}` expands to a different
instruction, so the `RUN` below it re-executes. The stale wheel comes from the
`--mount=type=cache` uv cache, which outlives the layer, and `uv sync` reuses the wheel it
already built for an unchanged source tree.

Reproduced with the Dockerfile's own command, `uv sync --frozen --no-editable`, against one
`UV_CACHE_DIR`:

```
sync 1: SETUPTOOLS_SCM_PRETEND_VERSION=1.0.0, cold cache   installed: 1.0.0
sync 2: SETUPTOOLS_SCM_PRETEND_VERSION=2.0.0, warm cache   installed: 1.0.0   <- stale
```

`uv pip install` against a path does not reproduce it; only the project workflow does,
which is what the Dockerfile runs.

The release page makes the case likely rather than remote. It tells the owner to tag
`v0.1.2rc1` and then `v0.1.2`, and both tags can name the same commit. The checkout is
then identical and only `VERSION` differs, which is exactly the case that serves the
stale wheel.

**The fix**, in both `pyproject.toml` files, as CodeRabbit wrote it:

```toml
[tool.uv]
cache-keys = [{ file = "pyproject.toml" }, { env = "SETUPTOOLS_SCM_PRETEND_VERSION" }]
```

**The two checks it had to pass.** Setting `cache-keys` replaces the defaults, so the risk
was trading a stale version for a stale source tree. Both were run on the probe:

```
with the cache key, version 2.0.0 on a warm cache   version 2.0.0   <- fixed
with the cache key, a changed source file only      marker second   <- source still tracked
```

`uv lock` resolves the same 147 packages and leaves `uv.lock` byte-identical.
`uv build --all-packages` still builds all four artefacts.

The harness `pyproject.toml` gets the same key. The image installs only the library, but
both distributions take their version from hatch-vcs, so both meet the same hazard
wherever a build sets the variable.

### The premise behind the `infrastore` floor

Earlier on 2026-11-19, before the work started, this run's author told the repository
owner that "this repository documents no infrastore format contract, the code reads time
series through the package's API". The owner chose `infrastore>=0.14.1` on that basis.

The claim is withdrawn. `infrastore` validates each time-series association row against a
SiennaSchemas wire contract whose version its own release selects, and
`import_time_series_associations_openapi` raises when the row does not match. The round
trip in the contract decision above is the evidence.
